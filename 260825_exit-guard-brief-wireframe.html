견적 폼은 이름·연락처·상세주소·평형대·예산·일정·지점까지 일곱 항목을 필수로 요구합니다. 처음 보는 사람에게는 부담스러운 분량이지만, 앞의 두 칸이 이미 채워져 있으면 시작 지점이 달라집니다. 이 설계의 핵심은 팝업이 접수를 대신하는 것이 아니라 폼의 출발선을 앞당기는 것입니다.

2. 언제 뜨는가: 뒤로가기 가드 방식

마우스가 화면 위로 빠져나가는 순간을 잡는 방식(mouseout)은 모바일에서 작동하지 않습니다. 그래서 G3와 동일하게 히스토리 엔트리를 한 칸 심어 두고 뒤로가기가 그 칸을 소비할 때 팝업을 띄웁니다. PC와 모바일이 같은 코드로 동작합니다.

진입 → history.replaceState({ d1Entry: 1 })
      → history.pushState({ d1Guard: 1 }) ← 뒤로가기가 먼저 먹는 칸

스택 [ d1Entry ] [ d1Guard ] [ d1Overlay(모달·라이트박스) ]

popstate 시 history.state 가 d1Entry 일 때만 팝업을 띄운다
  → 모달을 닫는 뒤로가기는 state 가 d1Guard 라서 그냥 지나간다 (충돌 없음)
상황 동작 G3 검증 결과
팝업을 닫고 다시 나가려 할 때 (같은 방문) 가드 엔트리를 다시 쌓아 재노출 (한 방문 3회까지) PC·모바일 정상
무시하고 나갔다가 다시 들어와 또 나가려 할 때 새 방문이므로 다시 노출 실측 확인
팝업이 뜬 상태에서 뒤로가기를 한 번 더 붙잡지 않고 그대로 내보냄 (탈출구) PC·모바일 정상

3. 뜨지 않아야 하는 경우

조건 처리
견적문의 페이지(/pages/estimates) 가드를 심지 않습니다. 팝업이 보내는 도착지이므로, 여기서 다시 띄우면 같은 요청을 두 번 하는 셈이 됩니다.
접수를 완료한 방문자 이번 방문은 sessionStorage.day1_lead_done, 이후 방문은 localStorage.day1_lead_done_at 으로 30일간 막습니다. 이미 상담을 신청한 고객에게 "견적 받아보세요" 를 다시 띄우면 안 됩니다.
팝업을 거쳐 폼으로 이미 넘어간 적이 있음 sessionStorage.day1_exitguard_carried 가 있으면 다시 띄우지 않습니다. 폼을 보다가 뒤로 나오는 동선에서 같은 팝업이 반복되면 방문자가 갇힌 느낌을 받습니다.
"다음에 볼게요"로 닫음 이번 방문에서만 억제합니다 (sessionStorage.day1_exitguard_dismissed). 팝업을 무시하고 나갔다가 나중에 다시 들어온 방문자는 새 방문이므로 다시 붙잡습니다. 재방문 자체가 관심이 남아 있다는 신호이고, 그때는 마음이 달라졌을 수 있습니다.
한 방문에서 세 번 띄움 더 붙잡지 않고 그대로 내보냅니다 (day1_exitguard_shown 상한 3회). 나가려는 사람을 계속 막아 세우면 팝업이 방해물이 됩니다. 이 상한도 방문 단위라 재방문하면 초기화됩니다.
어드민 등록 팝업이 이미 떠 있음 #popupRoot 에 열린 팝업이 있으면 건너뜁니다.
개인정보·이용약관 페이지 제외. 법적 고지를 읽는 중에 가리면 안 됩니다.

5. 도착 위치를 어떻게 고정하는가

값만 옮기고 화면이 엉뚱한 곳에 서 있으면 방문자는 고장으로 받아들입니다. 페이지 최상단에 서면 "왜 처음으로 돌아왔지"가 되고, 폼 한가운데에 서면 "내가 뭘 놓쳤나"가 됩니다. 도착 지점은 안내 배너 윗선으로 고정합니다. 배너·진행률·이미 채워진 두 칸·다음에 쓸 칸이 한 화면에 들어와야 흐름이 끊기지 않습니다.

처리 내용과 이유
URL 해시를 쓰지 않음 #estForm 앵커는 브라우저가 즉시 점프시키는데, 상단 고정 헤더(70px) 높이를 계산하지 않아 제목이 헤더에 가립니다. 해시 없이 ?from=exit 만 붙이고 위치는 코드로 잡습니다.
스크롤 복원 차단 history.scrollRestoration = "manual". 뒤로가기로 이 페이지에 다시 들어왔을 때 브라우저가 이전 스크롤 위치를 복원하며 우리가 잡은 위치를 덮어씁니다.
레이아웃 확정 후 이동 프리필을 끝내고 requestAnimationFrame 두 번을 기다린 뒤 좌표를 계산합니다. 폼 위쪽 히어로·프로세스 영역이 늦게 그려지면 계산해 둔 좌표가 밀리기 때문입니다.
이미지 로딩 보정 window.load 이후 한 번 더 위치를 확인하고, 목표 지점과 20px 넘게 어긋나 있으면 조용히 재보정합니다. 애니메이션 없이 즉시 이동해 튀는 느낌을 없앱니다.
계산식 목표 = 배너.offsetTop − 헤더높이 − 여백 16px. 헤더 높이는 상수로 박지 않고 getBoundingClientRect() 로 실측합니다. 모바일 헤더 높이가 다르기 때문입니다.
포커스 처리 PC: 상세주소 입력에 focus({ preventScroll: true }). 옵션이 없으면 브라우저가 제 마음대로 다시 스크롤합니다.
모바일: 포커스를 주지 않습니다. 키보드가 올라오며 화면이 절반으로 접혀 위치가 어긋나고, 방문자가 원치 않은 키보드를 닫는 동작부터 하게 됩니다.
실패 시 동작 배너나 폼을 찾지 못하거나 계산값이 문서 범위를 벗어나면 스크롤하지 않고 최상단에 그대로 둡니다. 엉뚱한 곳으로 튀는 것보다 안 움직이는 편이 낫습니다.
검증 방법 360 · 375 · 393 · 768 · 1440 다섯 가지 폭에서 도착 직후 화면을 캡처해, 배너와 상세주소 칸이 모두 보이는지 눈으로 확인합니다. (mobile-check 로 자동화)

6. 값을 어떻게 옮기는가

URL 쿼리로 넘기면 안 됩니다. ?name=임혜진&phone=01066246615 형태로 보내면 이름과 전화번호가 브라우저 히스토리, 리퍼러 헤더, 서버 접근 로그, GA4 착지 페이지 보고서에 그대로 남습니다. 개인정보가 분석 도구까지 흘러가는 사고이므로 이 방식은 배제합니다.
항목 내용
전달 매체 sessionStorage.day1_exitguard_carry 에 { name, phone, privacy, leadKey, ts } 를 담습니다. 탭을 닫으면 함께 사라지고 다른 사이트로 새지 않습니다.
읽는 곳 견적문의 페이지에서만 읽습니다. 다른 페이지에서는 이 값을 건드리지 않으므로, 방문자가 중간에 포트폴리오나 회사소개로 새도 엉뚱한 화면에서 폼이 채워지는 일이 없습니다.
1회용 처리 폼에 채운 즉시 삭제합니다. 남겨두면 방문자가 뒤로 갔다가 다시 들어올 때 이미 지운 값이 되살아나 덮어씁니다.
덮어쓰기 금지 폼에 이미 방문자가 입력한 값이 있으면 이관 값으로 덮어쓰지 않습니다. 작성 중이던 내용을 지우는 것이 가장 나쁜 오작동입니다.
만료 ts 기준 30분이 지나면 버립니다. 오래된 값이 다른 방문에 섞이지 않게 합니다.
수정 가능 여부 옮겨온 두 칸도 수정할 수 있게 둡니다. 오타를 고치지 못하면 연락이 닿지 않습니다. 화면에서는 "옮겨옴" 표시로 구분만 합니다.
동의 승계 팝업에서 받은 개인정보 동의를 폼에서 인정하고, 화면에는 동의한 사실을 표시합니다. 동의 이력(시각·경로)은 접수 레코드에 함께 남깁니다.

7. 팝업 단계에서 서버에 저장할 것인가

권장 A안 · 즉시 저장 후 승격

팝업에서 두 항목을 받는 즉시 저장하고 leadKey 를 발급합니다. 폼 제출 시 같은 키를 실어 보내면 서버가 그 레코드를 채워 넣고 Status 를 접수대기로 올립니다.

  • 폼에서 다시 이탈해도 이름·연락처가 남습니다.
  • 접수 안전망(불변규칙 1) 정신에 부합합니다. 방문자가 남긴 흔적을 잃지 않습니다.
  • 미완성분은 Status='작성중' 으로 두고 접수관리 기본 목록에서 숨깁니다. 별도 탭에서만 보이게 해 상담 카드가 오염되지 않게 합니다.
  • 30분이 지나도 완성되지 않으면 하루 한 번 묶어서 알립니다. 건마다 알리면 알림이 시끄러워집니다.
추가 구현: leadKey 발급·검증, 승격 갱신 경로, Status='작성중' 목록 분리, 만료 정리
대안 B안 · 폼 제출 시에만 저장

팝업은 값을 브라우저에만 담아 폼으로 넘기고, 서버 저장은 기존 견적문의 접수 한 번으로 끝냅니다.

  • 서버 변경이 사실상 없습니다. 가장 빨리 붙일 수 있습니다.
  • 미완성 카드가 생기지 않아 접수관리가 지금 그대로입니다.
  • 폼에서 이탈하면 연락처도 함께 사라집니다. 이탈 방지라는 목적의 절반을 포기하는 셈입니다.
  • 팝업이 실제로 얼마나 잡았는지는 exit_guard_submit 이벤트 수로만 알 수 있습니다.
추가 구현: 없음 (프런트만)

권장은 A안입니다. 이 팝업을 만드는 이유가 "떠나는 사람의 연락처를 확보하는 것"인데, B안은 폼 일곱 칸을 끝까지 채운 사람만 남기므로 기존 폼과 결과가 크게 다르지 않습니다. 다만 A안은 미완성 리드를 어떻게 다룰지가 함께 정해져야 합니다.

8. 접수 연동 명세 (A안 기준)

현재 /api/estimates 는 평형대·주소·일정·지점·예산을 모두 필수로 검증하고 하나라도 빠지면 validation_failed 로 떨어뜨립니다. 두 항목만 보내는 팝업 접수는 그대로 붙이면 전량 거부됩니다.

항목 내용
팝업 전송 필드 name · phone · privacy_agreed · form_type=exit_guard · 허니팟 _hp_field · 타임스탬프 _ts
Worker 검증 분기 form_type === "exit_guard" 일 때만 space_size·address·schedule·branch·budget 필수 검증을 면제합니다. 기존 견적 폼의 검증은 그대로 둡니다.
leadKey 서버가 난수 키를 발급해 응답하고 레코드에 저장합니다. 폼 제출 시 동봉되면 새로 만들지 않고 그 레코드를 갱신합니다. 이 키를 대조하지 않으면 팝업 접수와 폼 접수가 서로 다른 카드로 갈라집니다(Meta 리드의 MetaLeadId 와 같은 역할).
상태 전이 팝업 저장 시 Status='작성중' → 폼 제출 확정 시 '접수대기'. 승격 시각을 함께 남겨 팝업에서 완주까지 걸린 시간을 집계합니다.
중복 방지 leadKey 가 없는 상태로 같은 연락처가 30분 내에 다시 들어오면 새 카드를 만들지 않고 기존 '작성중' 레코드를 갱신합니다.
안전망 (불변규칙) 기존 4중 안전망을 동일하게 통과시킵니다. R2 estimates-attempts/ 원문 보관 · D1 저장 확정 후에만 200 반환 · 거부건도 흔적 남김 · 허니팟 단독 차단 금지. 새 경로라고 안전망을 우회하지 않습니다.
알림·문자 팝업 저장 단계에서는 고객 문자를 보내지 않습니다. 아직 접수가 끝나지 않았는데 "접수되었습니다" 문자가 가면 어긋납니다. 문자는 폼 완주 시점에 기존 홈페이지 본문 그대로 발송하고, 텔레그램 알림에는 [이탈팝업 경유] 표시를 붙입니다.
추적 노출 exit_guard_shown → 팝업 제출 exit_guard_submit → 폼 도달 exit_guard_form_view → 완주는 기존 규칙대로 서버 200 이후에만 generate_lead · 픽셀 Lead 를 발화합니다.

9. 무엇으로 성패를 판단하는가

단계 현재 판단 기준
① 팝업 노출 — 한 페이지만 보고 나가는 3,474세션 가운데 얼마가 실제로 잡히는지 먼저 측정합니다. 크롬 정책 때문에 전부 잡히지는 않습니다.
② 팝업에서 두 항목 입력 — 노출 대비 입력률. 문구와 브리프 구성의 성적표입니다.
③ 폼 완주 — 이 설계의 핵심 지표입니다. 입력한 사람 가운데 나머지 5항목까지 채운 비율. 여기가 낮으면 팝업이 아니라 폼 항목 수를 손봐야 합니다.
④ 월 접수 총량 41건 / 30일 기존 견적 폼 직접 접수가 줄지 않았는지 함께 대조합니다. 팝업이 정식 폼을 잠식하면 총량은 그대로인데 리드 질만 낮아집니다.
⑤ 통화 연결률 — A안을 택하면 미완성 리드가 쌓입니다. 완주 리드와 미완성 리드의 연결률을 나눠 집계해야 미완성분에 전화를 걸 가치가 있는지 판단할 수 있습니다.

10. 결정이 필요한 항목

  1. 부분 저장 여부 (7절) · A안(즉시 저장 후 승격)을 권장합니다. 선택에 따라 서버 작업량이 크게 달라집니다.
  2. 미완성 리드 운영 · 팝업만 남기고 폼을 마치지 않은 건에 담당자가 전화를 걸지, 통계로만 볼지 정해야 합니다.
  3. 브리프 네 항목 · 90건 / 2개 지점 / 8단계 / 3D 시뮬레이션으로 잡았습니다. 다른 강점(A/S 기간, 자재 등급 등)으로 교체할 수 있습니다.
  4. 노출 범위 · 전 페이지에 걸지, 포트폴리오·회사소개처럼 관심 신호가 있는 페이지에만 걸지 정해야 합니다.
  5. 버튼 문구 · "이어서 견적 신청하기"로 잡았습니다. 다음 화면이 더 있다는 사실을 감추지 않는 쪽이 이탈을 덜 부릅니다.
